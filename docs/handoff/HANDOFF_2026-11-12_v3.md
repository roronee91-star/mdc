## 0. 사용자와 일하는 방식 (가장 중요)

- 사용자(혜연)는 **코딩을 모른다.** 한국어로, 쉬운 말로 짧게 말한다. **질문은 한 번에 하나만.**
- 작업이 끝나면 **스크린샷을 보여 주고**(SendUserFile, display: render) **"마음에 들어요?"** 하고 묻는다.
- 사용자는 휴대폰 화면 캡처로 문제를 알려 준다. **빨간 동그라미가 문제 위치**다.
- 사용자가 말하는 중간에 고쳐 말하면(예: "저 판자는 엘리베이터 문이라 기둥만 조절하면돼") 그 말이 우선이다.
- **배포(사이트 반영)는 사용자가 "반영해줘"라고 할 때만** 한다. 배포 순서는 6장.
- **솔직하게** 말한다. 실수했으면 실수했다고 말한다(예: 11-10에 셰이더 미리 만들기가 오히려 더 버벅이게 했던 일 → 사과하고 뺐다).
- 확인 못 한 것은 확인 못 했다고 말한다. 특히 **실제 사이트(github.io)는 작업 컴퓨터에서 열리지 않는다(프록시 403)**. 배포 확인은 GitHub Actions 결과로만 하고, 사용자에게 "휴대폰에서 새로 고침해서 확인해 주세요"라고 부탁한다.
- 사용자가 "이 정도면 충분해"라고 하면 확인 안 된 작업은 넣지 않고 보관만 한다.

## 1. 지켜야 할 규칙

1. **Supabase Secret 키(secret / service_role)는 절대 받지 않는다.** 사용자가 붙여 넣으면 지우라고 하고 Publishable 키만 쓴다.
2. **건물 GLB 파일(`church-model-release-20261104.glb`)은 고치지 않는다.** 보정은 모두 **index.html 코드에서 화면에 그릴 때만** 한다.
3. 도면 PDF는 공개 저장소에 올리지 않는다.
4. 실제 찬송 음원이나 저작권이 남은 가사는 쓰지 않는다.
5. PR은 사용자가 말할 때만 만든다.
6. 커밋·코드·문서에 AI 모델 이름을 적지 않는다.
7. 움직임이 부드러운 것이 디자인보다 먼저다. 새 소품은 **decoKit으로 재질별로 합쳐서** 그리기 횟수를 늘리지 않는다(4장).

## 4. 꼭 알아야 할 기술 메모

- **버벅임의 원인과 지금 방식**
  - `renderer.compileAsync`(셰이더 미리 만들기)는 쓰지 않는다. 휴대폰에서 더 끊긴다.
  - 그림자: `renderer.shadowMap.autoUpdate = false`. `tickShadow(now)`가 필요할 때만 `needsUpdate`. 층·낮밤 바꿀 때는 `shadowDirty = true`. 검사용 `__dbg.shadow('auto'|'always'|'static')`, `__dbg.shadowRuns`.
  - 층 이동(`goToTourStep`) 때 지금 층 가구 무리만 보이고, 숨긴 무리는 `lazyMatrix`로 행렬 계산도 쉰다.
  - 측정(CPU 4배 느리게): 걸을 때 한 장면 JS 52~97ms → 17~36ms. 그리기 횟수 4층 약 1840 → 307~457, 지하 약 590 → 105~111 (+방송실 약 10).
- **decoKit(Y, parent)** (index.html 2013줄 근처): `d.box / cyl / ball / ring / put / mat`로 조각을 모은 뒤 `d.flush()`가 **재질별로 합쳐 메시 하나**로 만든다. 만든 메시는 `noHit`(누르기·걷기·카메라 판정 제외). 걷기를 막아야 하는 큰 가구는 따로 일반 메시로 둔다.
- **걷기 막힘**: `rebuildWalk()`가 보이는 메시의 경계 상자로 막힘을 정한다. `userData.pickOnly`(noHit)인 것은 제외. 합친 메시는 경계 상자가 커서 반드시 noHit이어야 한다.
- **trimRoofTops(root)**: 지붕 위로 솟은 GLB 부재 꼭짓점의 세계 높이를 14.3으로 누른다(파일은 그대로). 십자가(`CROSS_VERTICAL001/HORIZONTAL001`)는 1.3m 내림.
- **방송실 위치**: 지하 바닥 y = -6.6. 방 x -8.95 ~ -3.45, z -2.12(홀 쪽 유리창) ~ 0.08(남쪽 벽). 문은 동쪽 벽 z -1.15 ~ -0.3. 코드: `applyB1Fixes` 안 "6) 방송실(엔지니어룸)".
- **층 높이**: B1 -6.6, F1 0, F2 3.65, F3 7.25, F4 10.75, 지붕 약 14.1.

## 5. 남은 일 / 사용자에게 받을 답

1. **(답 기다리는 중) 방송실 디테일** `7718dfb` — "마음에 들어요?"에 대한 답. 좋다고 하고 "반영해줘"라고 하면 배포.
2. **휴대폰에서 버벅임 확인** — 11-10 수정 뒤 실제 휴대폰 느낌은 아직 못 들음. 여전히 버벅이면 다음 후보: 픽셀 배율(pixelRatio) 상한을 1.5로 낮추기.
3. **(제안만 함) 1층 바깥 나무·풀밭 다듬기** — GLB의 나무·풀밭이 아직 네모남. 옥상 정원처럼 코드에서 둥글게 덧그리기 가능. 사용자 답 없음.
4. 그 밖의 아이디어(사용자가 원할 때만): 처음 들어올 때·층 도착 때 보이는 시점 다듬기, 위쪽 메뉴 디자인, **서버(방) 고르기 기능 — 사용자가 "나중에"라고 미룸**.
5. 2판에서 이어진 것: AI 음악 파일로 찬양 바꾸기(사용자가 mp3를 주면), 나무 밑 바닥 조명 2판(pending 패치), 실제 기기 두 대로 접속·채팅·음성·불 켜기·기도제목 공유 확인.

## 6. 배포하는 법 ("반영해줘"를 들었을 때)

1. `git fetch origin main` 후 main이 작업 브랜치의 조상인지(fast-forward 되는지) 확인.
2. `git push origin HEAD:main`
3. 이 문서 3장 "배포 상태"의 `main` 해시와 내용을 고친다(2판 43줄도 쓰고 있다면 앞에 새 해시를 붙인다). 커밋하고 작업 브랜치에 push.
4. `mcp__github__actions_list`(list_workflow_runs, branch main)로 Pages 배포가 `success`인지 확인. 사이트 주소는 작업 컴퓨터에서 열 수 없으니 curl로 확인하지 않는다.
5. 사용자에게 "사이트에 올라갔어요" + 바뀐 것 + 주소 + "새로 고침해서 확인해 주세요".
- 배포가 시간 초과로 실패하면(11-10에 한 번 있었음) 문서 커밋을 하나 더 올려 다시 돌린다.

커밋 메시지 끝에는 세션이 알려 주는 Co-Authored-By / Claude-Session 줄을 붙인다.

## 7. 검사하는 법 (Claude용)

```bash
cd /home/user/mdc && python3 -m http.server 8008      # run_in_background, 2시간 지나면 꺼짐 → 필요할 때 다시 켬
cd tools/walk-check
node shotat.cjs <그림폴더> <장소> <이름> 카메라x,y,z 바라볼x,y,z [캐릭터x,y,z]
#   장소: step1(F1 횡단보도) step4(B1 본당) step6(F2) step5(F3) step7(F4)
#   밤 화면: T=night node shotat.cjs ...
#   예) 방송실을 홀에서: node shotat.cjs $S step4 user -6.2,-3.4,-6.0 -6.2,-6.0,-1.0 -6.2,-6.6,-3.0
```
- Playwright·chromium은 이미 깔려 있다(다시 설치하지 말 것). 실행 옵션 `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader`.

- 검사 전에 localStorage `mdc_name`, `mdc_gender`를 넣는다(shotat.cjs는 이미 넣음).
